# Memory Explorer

Memory Explorer is the visual interface for browsing, searching, and inspecting memories across your entire deployment. It gives your team direct visibility into what agents know, how memories were formed, and which facts are driving agent behavior, without writing queries against the database.

## Accessing Memory Explorer

Memory Explorer is available in the Memori Enterprise dashboard. Navigate to **Dashboard → Memory Explorer**.

Access is governed by your organization's ReBAC policy. Owners and admins have full access to Memory Explorer. Users can view memories within their assigned pools.

## What You Can Do

### Search and Browse

Search across all memories by entity, pool, keyword, or tag. Results show the memory content, its signal type, horizon, and when it was created and last recalled.

Filter by:

- **Entity**: view all memories for a specific user or agent
- **Pool**: inspect the contents of a Memory Pool
- **Memory type**: what the memory is about: a concept (Domain), person or thing (Entity), or task output (Process). Signal types within each memory:

  | Signal | Description |
  | ------ | ----------- |
  | **Constraint** | A rule or limit the agent must respect when acting or responding. |
  | **Fact** | A piece of information that is known to be true about the entity or domain. |
  | **Failure** | Something that was attempted and did not work, preventing the agent from repeating it. |
  | **Goal** | An objective the entity is trying to achieve, used to orient agent behavior. |
  | **Outcome** | The result of a completed action or decision, used to inform future reasoning. |
  | **Preference** | How the entity wants things done: tone, format, approach, or priority. |
  | **Strategy** | A higher-level approach the agent should apply when working toward a goal. |
  | **Workflow** | A sequence of steps or process the agent should follow for a given task. |
- **Horizon**: how long the memory persists. The three horizon types:

  | Horizon | Description |
  | ------- | ----------- |
  | **Decaying** | A memory that loses relevance over time and is deprioritized in recall as it ages. |
  | **Standing** | A persistent memory that remains equally relevant until explicitly updated or removed. |
  | **Volatile** | A short-lived memory tied to the current session or task, discarded once it is no longer needed. |

- **Date range**: memories created or updated within a window
- **Tag**: memories labeled with a specific tag

### Inspect Individual Memories

Click any memory to see its full detail:

- **Content**: the structured fact or summary
- **Source**: the session and conversation turn it was extracted from
- **Confidence**: the augmentation pipeline's confidence score
- **Recall count**: how many times this memory has been retrieved
- **Last recalled**: when it was last used to ground an agent response
- **Linked memories**: related facts in the knowledge graph

### Edit and Delete

Owners can edit memory content or permanently delete individual memories directly from the Explorer. Admins can remove memories from pools but cannot permanently delete them. All edits and deletions are recorded in the audit log with the acting user and timestamp.

### Knowledge Graph View

Switch to **Graph View** to see memories as a network. Nodes represent entities, facts, and relationships. Edges show how memories connect: which facts reference the same entity, which preferences were inferred from the same session, and how the knowledge graph evolved over time.

Graph View is useful for:

- Understanding why an agent responded the way it did
- Identifying contradictory or stale facts before they affect agent behavior
- Visualizing which users or topics have the densest memory coverage
